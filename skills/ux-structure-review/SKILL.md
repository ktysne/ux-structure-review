# UI 画面構造の 7 規則

利用者が画面のどこを見て、どれを押せばよいかを、まとまりと優先順位の構造から判断できるかを点検し、足りなければ補うためのスキルである。

## このスキルが守るもの

守るのは規則とその目的であり、特定の見た目ではない。
規則の説明に出てくる文言や画面構成は理解を助けるための例であり、色、余白、フォント、線、ボタンの位置そのものを揃える必要はない。

適用の可否は、対象アプリの性質（利用者、利用頻度、業務上の重要度、既存の UI 規約、技術的制約）を踏まえて判断する。
規則を機械的に当てはめると、単純な画面に区画や操作を増やしたり、既存のデザインシステムと異なる表現を持ち込んだりして、かえって構造を読みにくくする。
各規則の「対象外」と「別の表現で満たす条件」を確認してから提案する。

## 進め方

1. **対象の把握**：どの画面、コンポーネント、画面間フローを扱うかを特定する。
   アプリ全体の性質（業務システムか、一般消費者向けか、開発者向けか）と既存のデザインシステムや UI 規約を確認する。
   画面構成は、ルーティング、主要コンポーネント、画面上の順序、操作の入口から把握する。
2. **構造の洗い出し**：対象ごとに、情報のまとまり、繰り返し要素、役割の異なる区画、主操作、見出しと説明、手順や関係、前景と背景の重なりを列挙する。
   関連する要素、役割が異なる要素、同じ役割として扱う要素を区別し、画面上の距離、整列、面、階層、配置、接続を確認する。
3. **規則ごとの判定**：該当する構造について、[references/rules.md](references/rules.md) のチェック観点で現状を確認する。
   判定は「満たす」「満たさない」「適用しない（理由）」「情報不足（確認事項）」の四つに分ける。
   「適用しない」にできるのは、その構造が存在しないか、存在しても利用者が区別や優先順位を必要としない場合に限る。
   チェック観点どおりの表現がなくても別の手段で目的を達成できる場合は、rules.md の「別の表現で満たす条件」に従い、その手段の有無で「満たす」「満たさない」を決める。
   DOM の順序、キーボード操作の順序、共通コンポーネントの責務などが説明から分からない場合は、推測で判定せず「情報不足」として確認事項を添える。
4. **適用**：「満たさない」ものについて、そのアプリの UI 規約に沿った直し方を提案するか、依頼されていれば実装する。
   直し方は規則の目的から導き、色、余白、フォント、ピクセル数などの固定値を到達目標にしない。
5. **報告**：後述の形式で結果をまとめる。

レビューだけを依頼された場合は 4 を提案にとどめる。
実装を依頼された場合も、規則の適用可否に判断が分かれる箇所は提案として残し、確実な箇所だけを実装する。

## 7 つの規則

各規則の詳細なチェック観点、対象外の条件、別の表現で満たす条件、実装上の注意は [references/rules.md](references/rules.md) にある。
判定するときは必ず参照する。

| 番号 | 規則 | 目的 | 対象となる構造 |
|---|---|---|---|
| 01 | 関連を近づけ、違いを離す | 関連の有無を距離と整列から読み取れるようにする | 情報のまとまり、余白、整列、面の内側の配置 |
| 02 | 同じ役割を同じように見せる | 見た目の規則から同じ役割をすばやく見つけられるようにする | 繰り返し要素、同種の操作、同じ役割の表示 |
| 03 | 異なる役割を面で分ける | 役割の違う情報を混同せずに扱えるようにする | 複数の責務や文脈を持つ画面の区画 |
| 04 | 次の操作を一つに絞る | 次に進む操作を迷わず選べるようにする | 複数の操作が並ぶ画面、フォーム、フローの操作列 |
| 05 | 情報の階層で読む順番を作る | 見出しから詳細へ読む順番を作り、内容の関係を追えるようにする | ページ見出し、セクション見出し、説明、補足、左端の整列 |
| 06 | 手順と関係を配置でつなぐ | 手順や関係の向きと順序を誤解なく読み取れるようにする | ステップ、依存関係、フロー、接続線、配置順 |
| 07 | 重要な要素を背景から際立たせる | 注目すべき要素と背景を区別し、操作対象へ集中できるようにする | ダイアログ、ポップオーバー、重要な通知、重なり合う要素 |

## 適用判断の原則

規則を当てはめるかどうかは、次の順で考える。

- **その構造が実際に必要か**：要素が数個しかなく関係が明らかな画面や、単一操作の画面に規則を機械的に足さない。
- **利用者が区別や優先順位を必要とするか**：区別する対象がなく、どの操作を選ぶかで迷わないなら、規則の目的が成立しない。
- **既存の規約と衝突しないか**：アプリにデザインシステムや共通コンポーネントがあるなら、その構造と語彙で実現する。
  規則の目的を満たす別の表現が既にあるなら、それを「満たす」と判定してよい。
- **コストに見合うか**：構造を変えるためにルーティング、コンポーネント API、データの並び、アクセシビリティ情報まで変更する必要がある場合がある。
  その場合は、画面だけで直せる部分と追加開発が必要な部分を分けて提案する。

美的ユーザビリティ効果は美しい見た目が使いやすい印象に影響することを示すが、見た目の評価と操作の成功は別に確認する。
判断に迷ったときは、規則の目的（表の「目的」列）に立ち返る。
目的が満たされていれば手段は問わない。

## 報告の形式

レビュー結果は次の形式でまとめる。
対象が多い場合は画面ごとに繰り返す。

```markdown
## 対象
（画面やコンポーネントの名前と、アプリ全体の性質の要約）

## 判定
| 規則 | 判定 | 現状 | 提案 |
|---|---|---|---|
| 01 関連と距離 | 満たさない | ラベルと入力欄の間隔が、項目同士の間隔と同じ | 項目内の間隔を項目間より詰め、まとまりを示す |
| 04 主操作 | 満たす | 送信ボタンだけが強調され、戻るは補助操作 | なし |
| 06 手順と関係 | 適用しない | 手順や依存関係を示す要素がない | なし |
| 07 前景と背景 | 情報不足 | ダイアログのフォーカス移動先が実装から読み取れない | 共通ダイアログの仕様を確認してから再判定 |
| ... | | | |

## 優先して直す項目
（利用者が誤った操作を選ぶ可能性と、迷いが発生する頻度が大きい順に、理由を添えて）

## 判断を委ねる項目
（適用の可否や実装方法がアプリの方針に依存するもの。選択肢と推奨を添えて）
```

「判断を委ねる項目」には、区画を増やすか既存の共通コンポーネントを拡張するか、画面内の主操作を変えるか業務フローを変えるかなど、開発者が決めるべきことを残す。
自走中はメインセッションの判断で推奨案を採り、決めるべき内容は一覧にして開発者に提示する。

## 実装時の注意

- 文言は、そのアプリの既存の文言のトーン（敬体か常体か、専門用語の使い方）に合わせる。
- 情報のまとまりは、見た目だけでなく意味のある HTML 要素、見出し、ランドマーク、アクセシビリティ名でも伝える。
  視覚的な距離や面と DOM の構造、読み上げ順、キーボード操作の順序が食い違うと、利用者によって受け取る画面構造が変わる。
- 同じ役割を共通化するときは、見た目の再利用だけでなく、ラベル、操作の意味、フォーカス順もそろえる。
- 画面幅が変わっても、関係する要素のまとまりと手順の順序が保たれるかを確認する。
  横並びを縦並びに変える場合も、配置の変化が実際の関係の変化を意味しないか確認する。
- ダイアログやポップオーバーは、前景の範囲、背景の操作可否、フォーカスの移動先を構造上の意味と一致させる。
- 面やカードを増やすだけで構造を伝えようとせず、既存の見出し、整列、余白、順序で目的を満たせないかを先に検討する。
- 変更後は、画面を目で追うだけでなく、キーボード操作と支援技術で読み上げられる順序を確認する。

読み込み中、空、0 件、失敗、権限不足、保存状態、削除、完了、入力不備の表示や遷移は ux-state-review で扱う。
構造レビュー中にそれらへ気付いた場合は、このスキルの判定に取り込まず、ux-state-review に委ねる事項として報告する。
